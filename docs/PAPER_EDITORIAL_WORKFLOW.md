# Paper editorial workflow

Phase36 is prepared locally and has not been applied to a database. The hosted editor must show an unavailable state until its schema and permissions exist. No real source-check, approval, or publication action was performed in this implementation pass.

Platform administrators hold the editorial capability. The private workflow and audit tables are readable only by those editors; anonymous users and ordinary members cannot read evidence. Direct authenticated writes to these tables are revoked. Only the authenticated, role-checked RPC records transitions.

The editor loads a paper, its revision hash, and a workflow decision token in one database statement, displays the exact text and source evidence, and submits both tokens with every decision. The database locks the paper before its workflow, recomputes the content hash, and rejects stale decisions. A new decision token is generated after every workflow action and material edit. Replacing source evidence and returning to the same state therefore invalidates an old approval form even when the paper text is unchanged. Actor identities and action times come from the authenticated session and database clock. Human attestations start unchecked; fetching a source or producing an AI draft never records human approval.

The sequence is draft → source checked → editorial pending → approved → published. Source checking requires complete-paper, appendix and figure attestations, a full-text URL and checksum, source version and license, checking notes, AI disclosure, and at least three claim-level citations. Structural checks require authors, a primary HTTPS source, a descriptive summary, 700–1200 review words, and eight headed sections. These checks cannot establish scientific validity; the human source check and editorial decision remain necessary.

Approval is an explicit human decision with a rationale; publishing is a separate action. The same authorized editor may perform the two actions, but neither is inferred. Any material paper-text or metadata change clears current checks and approval, returns the item to draft, and unpublishes it. Previous evidence remains in the audit history. Withdrawn items require a return to draft and fresh checking before republication. Audit records retain the paper's original identity even if its content row is deleted.

Existing public database rows are labeled `legacy_published` without backfilled checks or approval. They retain existing visibility until edited or withdrawn. This is historical continuity, not an assertion that they satisfy the new review standard. Their legacy state is visible in the editor. All newly authored local reviews remain in the separate private corpus and are not uploaded by this migration.

Deployment verification: apply phase36 and the phase37–38 security hardening only to the intended project after owner approval, run `supabase/VERIFY_SETUP.sql`, then run `supabase/VERIFY_PAPER_EDITORIAL.sql` on staging. The latter is a rollback-only integration script covering direct-write denial, missing evidence, stale decisions, separate approval/publication, material-edit invalidation, role denial, anonymous denial, and audit retention. It contains explicit synthetic fixture attestations and does not approve actual research. It has not been executed in this pass. Local tests exercise form gates, RPC-only client behavior, ambiguous response rejection, and migration-chain alignment. Browser and live-role verification remain deployment checks.

The explicit runner is `bun run supabase:paper-editorial -- --staging`, using matching configured public/database project identities. It refuses to open a connection without the staging flag, has bounded timeouts, and rolls back on failure as well as success. It is not called by builds, local unit tests or release checks. Passing the flag selects the operator's staging configuration; it cannot independently certify that a project is disposable.

All 100 private local reviews have a deterministic, reviewable hosted-draft mapping at `research/paper-reviews/exports/platform-drafts.json`. Its adjacent README documents exact field mapping, duplicate checks, and human review steps. `python3 scripts/paper-export-drafts.py --check` detects stale mappings. This artifact performs no database inserts or editorial transitions.
